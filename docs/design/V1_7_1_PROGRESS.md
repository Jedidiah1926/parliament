## 3. 1 ~ 2단계: 성능

### 무엇이 느렸나 (측정으로 확인한 것)

1. **자동저장이 가만히 있어도 15초마다 세이브 전체를 다시 썼습니다.** `getAppState()`가 부를 때마다 `meta.savedAt`에 새 시각을 찍는데, “바뀐 게 없으면 건너뛰기” 비교가 그 시각까지 포함해 견줬기 때문입니다. 큰 세이브(6.36MB)에서 15초마다 0.7초씩 멈췄습니다.
2. **저장 한 번이 목록 전체를 다뤘습니다.** `saveActiveNow` → 모든 세이브 상태를 파싱 → 목록 전체를 다시 직렬화 → 저장소 쓰기(한도 초과로 실패) → 바뀐 세이브를 JS로 통째 압축 → 다시 쓰기 → 저장 목록 화면을 그리며 목록을 세 번 더 파싱.
3. **세계지도는 구역 하나를 칠할 때마다 2번을 그 자리에서 했습니다.** 붓질 한 걸음마다 0.7 ~ 1.5초.
4. **탭을 옮길 때마다 보이지 않는 목록까지 전부 다시 그렸습니다.** `switchSubTab` → `refreshUI()` → 정당 정보 · 대표 · 이념 · 연정 · 원별 정당 목록(큰 세이브에서 약 93ms)을 어느 탭에 있든 매번.
5. **데스크톱 앱은 저장마다 메인 프로세스가 모든 세이브를 다시 직렬화 · 해시하고, 바뀐 세이브를 gzip 9단계로 압축했습니다**(화면은 그동안 동기 IPC로 멈춤). 큰 세이브 둘 · 작은 세이브 하나에서 저장당 약 590ms, 바뀐 게 없어도 약 130ms.

### 확인하지 못한 것 · 남은 문제

- **Electron에서 실행해 보지 못했습니다.** 이 작업 환경에는 Electron이 없습니다. `saves:write-slot`의 메인 프로세스 쪽 논리는 Node에서, 화면 쪽 논리는 가짜 앱으로 각각 시험했지만 **실제 창에서의 IPC 왕복 · 저장 폴더 기록은 확인 전**입니다. 출시 전에 데스크톱 빌드에서 큰 세이브 저장 → 앱 다시 열기 → 이름 바꾸기 → 저장을 직접 확인해야 합니다.
- 큰 세이브의 강제 저장 한 번(`saveActiveNow(true)` — Ctrl+S, 이벤트 선택, 결정)은 아직 약 420ms입니다(상태 수집 · 직렬화 약 70ms + 압축 약 130ms + 쓰기).
- 탭 전환 p95(약 580ms)는 그대로입니다 — 구성 › 목록 · 내각 › 각료 · 경제 › 개요는 그 화면 자체를 그리는 데 200 ~ 300ms가 듭니다.
- 제작기에서 이벤트 500개의 이벤트 탭은 한 번에 3.6 ~ 4.8초 멈춥니다(모든 입력 양식을 한꺼번에 만듦). 실행 취소도 약 90 ~ 150ms.
- 지도 5,000구역의 다시 그리기 · 색 바꾸기는 목표(p95 33ms)에 못 미칩니다.
- 메모리 사용량 · 지도/트리 이동 프레임 시간 · 이미지/맵 가져오기는 재지 않았습니다.
